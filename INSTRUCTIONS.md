# Kernnews — инструкция по ежедневному отчёту

## 1. Цель

Каждый день собирать на русском языке короткий, высокосигнальный отчёт по AI, разработке, мобильным приложениям, продукту, росту, бизнесу, hardware и low-level engineering.

Главный принцип: **лучше пропустить материал, чем добавить слабый, повторный, неактуальный или плохо проверенный**.

Отчёт должен быть понятен без открытия ссылок, но не превращаться в длинный пересказ.

## 2. Временное окно и защита от повторов

Основное окно — материалы, релизы и запуски, появившиеся или ставшие заметными с прошлого выпуска, обычно за последние 24 часа.

Перед каждым новым отчётом обязательно:

1. Открыть в `p0dyakov/kernnews` последние **3 существующих файла `YYYY-MM-DD.md`**.
2. Проверить уже показанные URL/canonical URL, статьи, модели, продукты, компании, кейсы и underlying events.
3. Не повторять материал только потому, что он снова поднялся на HN, получил больше upvotes или появился на другом сайте.
4. Повтор разрешён только при существенном новом развитии: новый релиз, независимый benchmark, крупные новые цифры, сделка, технический результат и т. п.
5. Дедуплицировать также между разделами текущего выпуска.

Практическое правило: последние **72 часа** — обязательная зона проверки на повторы.

## 3. Общие правила ресёрча

- Никогда не выбирать материал только по заголовку, сниппету, points/upvotes или месту в рейтинге.
- Перед включением читать полный первичный материал.
- Проверять важные цифры по первичным источникам.
- Если контекста не хватает — собирать его по дополнительным сайтам.
- Маркетинговые заявления компаний не выдавать за независимый факт.
- Если материал невозможно нормально прочитать — не включать.
- Не добавлять научные AI-paper как отдельный раздел.
- Не заполнять разделы искусственно.

## 4. Стиль и формат

**Таблицы не использовать.**

Каждый выпуск — обычный минималистичный Markdown-текст.

Обязательная структура:

```md
# Короткий заголовок выпуска

_дата_

## Раздел

### [Название материала](ссылка)
[Дополнительная ссылка / метрики](ссылка)

Короткое саммари.

> **Комментарии**
> Короткая выжимка комментариев.
```

Правила:

- У каждого ежедневного выпуска есть **короткий заголовок**, суммирующий самые важные новости дня.
- Заголовок не должен преувеличивать результат и создавать дезинформацию.
- Если цифра относится к одному benchmark/kernel/test, это должно быть ясно из формулировки.
- Всё на русском.
- Простые слова.
- Английские термины — только когда естественно.
- Никакой вводной воды: «интересный материал», «важный момент», «здесь спорят» и т. п.
- Сразу факты.
- Саммари — обычно 2–4 коротких предложения.
- Если в целом в разделе ничего достойного нет: `Ничего нового`.
- Если у конкретного HN-материала нет содержательных комментариев: `Ничего нет`.

Цель по размеру: весь ежедневный выпуск должен по возможности помещаться в **одно Telegram-сообщение до 4096 символов после форматирования**.

## 5. Приоритет тем

### Максимальный приоритет

1. Новые AI-модели и заметные capability jumps.
2. Coding agents, autoresearch, agentic engineering.
3. Практические devtools и новые способы разработки.
4. Mobile/iOS, App Store, Swift, React Native, Flutter.
5. Subscription apps, paywalls, pricing, retention, LTV, CAC.
6. Growth: TikTok, Meta, Apple Ads, ASO, distribution.
7. Founder/business cases с конкретной экономикой.
8. Product ideas, PMF, monetization.
9. AI infra, chips, inference, datacenters.

### Второй приоритет

- UX/UI и продуктовый дизайн;
- compilers/OS/CPU/ISA;
- hardware и low-level engineering, **только если вывод достаточно крупный и полезный**.

### Обычно не брать

- технические curiosities;
- историю Unicode/стандартов без прямой современной ценности;
- единичные bug hunts конкретного shell/tool;
- случайные consumer gadgets;
- generic maker stories без сильной экономики/вывода;
- просто необычный инженерный факт;
- пост, который интересен узкой аудитории, но не даёт полезного вывода для founder/developer.

## 6. Новые AI-модели

Включать только:

- новую модель;
- существенную новую версию;
- заметный capability jump существующей модели.

Отслеживать:

- text/reasoning;
- coding;
- multimodal;
- image;
- video;
- audio/voice;
- robotics/embodied — только major releases.

Особенно внимательно: китайские лаборатории и open-weight ecosystem.

Для каждой модели:

### **Название модели**

Коротко: кто выпустил, что умеет, что изменилось, доступность/цена при необходимости.

**Бенчмарки:** независимое сравнение с актуальными top performers. Если независимых данных ещё нет — так и написать, отдельно указав developer-reported results.

Если достойных релизов нет:

`Ничего нового`

## 7. Hacker News

HN — **не список популярных постов**, а источник кандидатов. Порог отбора высокий.

### Материал проходит только если выполняется хотя бы одно

- даёт сильный новый результат по AI/coding agents;
- показывает реально полезную новую технологию/dev workflow;
- содержит важный бизнес/founder/growth кейс с конкретными цифрами;
- даёт крупный вывод по mobile/platforms/chips/infra;
- это большой технический разбор, который реально меняет понимание важной технологии.

### Материал не проходит, даже если набрал много points, если это

- просто любопытная история;
- niche bug hunt;
- исторический/Unicode/языковой curiosity;
- случайный гаджет;
- indie story без сильных цифр или применимого вывода;
- узкая техническая тема без влияния на текущую работу/бизнес/индустрию.

**Перед финальным включением спросить:**  
`Я бы реально хотел получить push-уведомление именно об этом материале?`  
Если нет — убрать.

Не пытаться набрать определённое число HN-постов. **2 сильных лучше 6 средних.**

Для каждого кандидата:

1. Прочитать полный материал.
2. Прочитать содержательные HN-комментарии.
3. При необходимости собрать дополнительный контекст.
4. Указать HN points/comments.

Формат:

```md
### [Название](ARTICLE_URL)
[HN · N points / M comments](HN_URL)

2–4 предложения по сути.

> **Комментарии**
> 1–3 самых полезных аргумента/контраргумента.
```

Комментарии должны содержать только:

- сильные контраргументы;
- опыт других инженеров/фаундеров;
- дополнительные факты;
- реальные ограничения;
- полезные альтернативы.

Если ничего содержательного нет:

```md
> **Комментарии**
> Ничего нет
```

## 8. Indie Hackers

Отбирать только сильные кейсы про:

- PMF;
- pricing;
- growth/acquisition;
- monetization;
- SaaS/mobile;
- founder stories;
- unit economics;
- distribution/sales;
- реальные цифры бизнеса.

Комментарии Indie Hackers не нужны.

Для каждого материала обязательно отдельно собрать контекст по бизнесу: официальный сайт, pricing, профиль основателя, App Store/Google Play, интервью, независимые статьи и другие публичные данные.

Формат:

```md
### [Название статьи](INDIE_HACKERS_URL)
[Продукт / бизнес](PRODUCT_URL)

Короткое, но самодостаточное объяснение: что за продукт, кому нужен, как зарабатывает, ключевые цифры, что сработало у основателя и главный практический вывод.
```

Если достойного материала нет:

`Ничего нового`

## 9. Product Hunt

Product Hunt — discovery-source, а не готовый рейтинг.

Для каждого кандидата:

1. Прочитать PH page.
2. Открыть сайт продукта.
3. Для technical/open source — посмотреть repo/docs.
4. Проверить, что это не старый relaunch.
5. Сравнить с очевидными аналогами.

Отсекать:

- generic AI wrappers;
- AI slop;
- клоны;
- thin UI над API;
- мелкие утилиты без реальной ценности;
- повторы прошлых выпусков;
- дубли других разделов.

### Саммари должно быть очень коротким

Сразу ответить простыми словами:

1. **Что это?**
2. **Что конкретно даёт пользователю?**

Обычно **1–2 предложения**. Не перечислять второстепенные функции.

Формат:

```md
### [Название](PRODUCT_HUNT_URL) · **N upvotes**
[Сайт](PRODUCT_URL)

Что это и что даёт — 1–2 коротких предложения.
```

Если repo важнее сайта, можно дать `Сайт / GitHub`.

Если ничего достойного нет:

`Ничего нового`

## 14. Telegram CI/CD

Workflow: `.github/workflows/telegram.yml`

При добавлении нового root-файла `YYYY-MM-DD.md` в `main`:

1. прочитать Markdown;
2. преобразовать его в поддерживаемое Telegram Bot API форматирование;
3. отправить **текстом через `sendMessage`**, а не как document;
4. отключить link previews;
5. обычные Markdown blockquotes из блока `> **Комментарии**` отправлять как **expandable blockquote**, чтобы комментарии были свёрнуты по умолчанию;
6. сохранить bold/italic/inline links;
7. не отправлять `INSTRUCTIONS.md`;
8. если итоговый текст превышает лимит Telegram, workflow должен завершиться ошибкой, а не незаметно резать смысл на части.

Для ручной повторной отправки workflow должен поддерживать `workflow_dispatch`.

## 15. Важное ограничение на текущем этапе

Пока формат отчёта дорабатывается, **не изменять постоянную scheduled task**, если пользователь отдельно явно не попросил синхронизировать эту инструкцию с автоматизацией.
