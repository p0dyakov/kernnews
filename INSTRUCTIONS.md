# Kernnews — источник истины

Этот файл — **единственный источник истины** для ежедневного отчёта Kernnews.

Scheduled task в начале каждого запуска заново читает актуальный `INSTRUCTIONS.md` из `p0dyakov/kernnews` и выполняет его буквально. Не дублировать бизнес-логику в prompt scheduled task и не использовать старую/закэшированную версию.

Если `INSTRUCTIONS.md` недоступен — отчёт не собирать и не импровизировать.

Любое согласованное изменение формата, отбора, источников, дедупликации или публикации сразу вносить сюда.

---

## 1. Цель

Каждый день собирать на русском высокосигнальный отчёт по AI, разработке, продукту, growth, бизнесу, hardware и low-level engineering.

Главный принцип: **лучше пропустить материал, чем добавить слабый, повторный, неактуальный или плохо проверенный**. Два сильных материала лучше шести средних.

Отчёт нужен не только для утилитарной пользы здесь и сейчас, но и для насмотренности, понимания трендов, новых бизнес-моделей и расширения кругозора.

## 2. Окно и дедупликация

Не использовать фиксированное правило «последние 24 часа». Основное окно — **всё новое с момента фактического создания предыдущего отчёта до текущего запуска**.

Перед ресёрчем:

- определить текущую дату в `Europe/Moscow` — это дата файла текущего выпуска;
- найти самый свежий существующий `YYYY-MM-DD.md` с датой раньше даты текущего выпуска;
- найти commit, в котором этот предыдущий файл был впервые добавлен в `main`, и использовать timestamp этого commit как `window_start`;
- `window_end` — фактическое время текущего запуска;
- если предыдущего выпуска нет или timestamp его создания получить нельзя, fallback: предыдущая дата выпуска в `11:15 Europe/Moscow`; если и её нет — последние 24 часа;
- если автоматизация пропустила один или несколько дней, следующий выпуск обязан покрыть весь пропущенный интервал;
- при повторном запуске в тот же день и существующем сегодняшнем файле всё равно строить окно от предыдущего датированного выпуска, чтобы сегодняшний отчёт можно было полностью пересобрать.

Перед каждым выпуском обязательно:

- прочитать последние **3 существующих `YYYY-MM-DD.md`**; если их меньше — прочитать все;
- проверить уже показанные URL/canonical URL, статьи, модели, продукты, компании, кейсы и underlying events;
- не повторять историю только потому, что она снова поднялась на HN, набрала больше upvotes или появилась у другого источника;
- повторять только при существенном новом развитии: новый релиз, сильный независимый benchmark, крупные новые цифры, сделка, новый технический результат;
- дедуплицировать также между разделами текущего выпуска.

Последние **72 часа** — обязательная зона усиленной проверки на повторы, но при пропуске автоматизации проверять весь интервал с прошлого отчёта.

## 3. Ресёрч, retrieval и точность

- не выбирать материал только по заголовку, сниппету, points/upvotes или рейтингу;
- перед включением читать полный первичный материал;
- важные цифры проверять по первичным источникам;
- если контекста не хватает — собирать его по дополнительным сайтам;
- маркетинговые заявления не выдавать за независимый факт;
- если конкретный материал нельзя нормально прочитать или проверить — не включать;
- отдельный раздел научных AI papers не делать.

### Надёжность retrieval

Ошибка прямого открытия URL, `403`, `cache miss`, пустая JS-оболочка или устаревший поисковый сниппет **не означают, что источник проверен и в нём ничего нет**.

Для обязательного discovery-источника последовательно использовать:

1. точный canonical/listing/archive URL из этого файла;
2. другой официальный listing/archive/feed/API endpoint, указанный ниже;
3. навигацию по официальному сайту от доступной страницы;
4. domain-restricted web search по этому же источнику;
5. если ниже явно указан сторонний fallback — использовать его только для discovery, после чего обязательно открыть и проверить первичную страницу кандидата.

Не прекращать обход после первого технического сбоя. Техническая недоступность одного discovery-источника сама по себе не является основанием объявить весь раздел пустым.

`Ничего нового` по разделу допустимо только после фактического обхода предусмотренных источников и проверки найденных кандидатов. Если обязательный источник после всех fallback-путей всё равно нельзя полноценно проверить, продолжить отчёт по остальным источникам, не выдумывать данные и в **служебном результате запуска** отдельно назвать неполностью проверенный источник и причину. В Telegram digest служебную информацию не помещать.

Перед финальным commit ещё раз проверить временное окно, последние 3 выпуска, дедупликацию, открываемость всех включённых URL, подтверждение ключевых фактов и то, что пустые разделы пусты по содержанию, а не из-за retrieval-сбоя.

## 4. Общий формат

**Таблицы не использовать.** Файл — готовый минималистичный Markdown-пост.

**Дату внутри выпуска не писать.** Дата хранится только в имени файла `YYYY-MM-DD.md`.

Файл и Telegram-пост начинаются сразу с первого непустого `##` раздела. Никакого `#`-заголовка выпуска и отдельной строки с датой.

### Порядок разделов

Порядок фиксированный:

- AI-модели;
- Новости;
- Авторы;
- Indie Hackers;
- Бизнесы;
- Product Hunt;
- Hacker News.

Пустые разделы пропускаются, остальные сохраняют этот относительный порядок.

### Переносы

- пустая строка используется только между разделами;
- внутри одного раздела материалы идут подряд без пустых строк между ними;
- между названием материала, саммари и комментариями пустых строк не делать;
- перед финальной строкой `Ничего нового: ...` обязательно одна пустая строка;
- в самих отчётах списки оформлять длинным тире `—`, не `-` и не `•`.

### Пустые разделы

Пустой раздел отдельно не выводить. Все пустые разделы объединять в самом конце одной строкой и перечислять в порядке разделов.

Пример:

```md
Ничего нового: AI-модели, Авторы, Indie Hackers и Бизнесы.
```

Если пустой раздел один:

```md
Ничего нового: Indie Hackers.
```

Если пустых разделов нет — строку не добавлять.

### Стиль

- всё на русском, кроме естественных названий/терминов;
- простые слова;
- никакой вводной воды: «интересный материал», «важный момент», «здесь спорят», «стоит отметить»;
- сразу факты;
- HN-саммари подробные и самодостаточные;
- Новости и Product Hunt — короткие;
- не повторять одну мысль разными словами;
- если у конкретного HN-поста нет содержательных комментариев: `Ничего нет`.

Цель — помещать выпуск в одно Telegram-сообщение до ~4000 символов после рендера. Если места не хватает, сначала убирать менее важный материал, а не урезать сильный HN-пост до потери смысла.

## 5. Приоритет тем

- новые AI-модели и реальные capability jumps;
- coding agents, autoresearch, agentic engineering;
- практические devtools и новые способы разработки;
- subscription apps, paywalls, pricing, retention, LTV, CAC;
- growth: TikTok, Meta, Apple Ads, ASO, distribution;
- founder/business cases с конкретной экономикой;
- новые и необычные бизнес-модели в любых вменяемых нишах;
- consumer brands, physical products, ecommerce, retail, food, services, marketplaces, manufacturing;
- product ideas, PMF, monetization;
- AI infra, chips, inference, datacenters;
- hardware и low-level engineering.

Обычно не брать:

- technical curiosities;
- историю Unicode/стандартов без прямой современной ценности;
- единичные bug hunts конкретного shell/tool;
- случайные novelty-gadgets без бизнес-потенциала;
- generic maker stories без сильной экономики или вывода;
- узкую тему без заметной пользы для founder/developer или расширения бизнес-кругозора.

## 6. AI-модели

Включать только новую модель, существенную новую версию или заметный capability jump.

Отслеживать text/reasoning, coding, multimodal, image, video, audio/voice; robotics/embodied — только major releases.

### Discovery / verification

Проверять официальные лаборатории и репозитории, а также:

- Artificial Analysis models leaderboard — https://artificialanalysis.ai/leaderboards/models/
- Epoch AI benchmark hub — https://epoch.ai/benchmarks
- Epoch AI benchmark search; сортировка `Newest added` при необходимости — https://epoch.ai/benchmarks/search
- Hugging Face, недавно созданные модели — https://huggingface.co/models?sort=created
- ModelScope model catalogue — https://www.modelscope.cn/models

ModelScope OpenAPI по умолчанию не использовать как обязательный путь: `https://www.modelscope.cn/docs/openapi` требует bearer token. Если токен когда-либо будет отдельно настроен, API можно использовать как дополнительный discovery-путь, но не заменять им проверку официального model card/release.

Формат:

```md
## AI-модели
### Название модели
Кто выпустил, что изменилось, для чего модель и доступность/цена, если важно.
**Бенчмарки:** независимое сравнение с актуальными top performers. Если независимых данных нет — прямо это написать и отдельно обозначить developer-reported результаты.
```

Если сильных релизов нет — раздел не выводить; добавить `AI-модели` в финальную строку.

## 7. Новости

Искать новости **по всему интернету** по всем темам из раздела «Приоритет тем». Не ограничиваться заранее заданным списком сайтов.

AI News / smol.ai — https://news.smol.ai/ — использовать как один из discovery-источников, а не как основной или единственный источник.

Для каждого кандидата:

- найти и открыть первичный источник новости;
- проверить ключевой факт по первичному источнику;
- при необходимости сверить информацию с несколькими независимыми источниками;
- не включать слухи как факт;
- не дублировать модель, HN-материал, Product Hunt-продукт, бизнес или авторский пост из другого раздела;
- брать только реально значимые новости по темам из раздела «Приоритет тем».

Саммари — обычно **1–3 предложения** и только фактическое содержание: что произошло, кто участвует, ключевые суммы/цифры/условия и необходимый контекст.

**Не добавлять собственный вывод, мораль, практический сигнал или интерпретацию в конце.** Если значимость новости невозможно понять из самих фактов без авторской интерпретации — лучше не включать её.

Формат:

```md
## Новости
### [Короткое название новости](PRIMARY_SOURCE_URL)
Факты и необходимый контекст — 1–3 коротких предложения, без аналитического вывода от автора отчёта.
```

Если сильных новостей нет — раздел не выводить; добавить `Новости` в финальную строку.

## 10. Бизнесы

Цель раздела — расширять бизнес-насмотренность за пределами software/startup bubble: видеть новые потребительские бренды, физические продукты, hardware, ecommerce, услуги, food, retail, manufacturing, marketplaces и другие понятные бизнес-модели.

### Обязательные discovery-источники и точные пути

На каждом ежедневном запуске обязательно проверить **все** источники ниже, даже если сильные кандидаты уже найдены раньше. Только после полного обхода объединить кандидатов, дедуплицировать и выбрать лучшие.

- **Kickstarter / Just Launched** — canonical: https://www.kickstarter.com/discover/newest . Kickstarter может отдавать web-retriever `403`. Если direct fetch не работает, использовать https://backerlens.com/discover как сторонний discovery-fallback для `NEW LAUNCHES · LAST 72H` и/или domain-restricted search по `kickstarter.com/projects/`. BackerLens не является источником истины: перед включением обязательно открыть официальную Kickstarter project page и проверить продукт, rewards/pricing, backers и raised там. Не считать пустой `403` проверкой Kickstarter.
- **BackerKit / Just Launched** — primary: https://www.backerkit.com/c/feeds/just_launched/projects . Secondary: https://www.backerkit.com/c/feeds/all_time/projects?sort_by=recently_launched . Если один endpoint даёт cache miss, использовать второй и открывать конкретные project pages.
- **Wefunder / Newest** — primary: https://wefunder.com/explore/marketplace , выбрать `Newest` и проверить `New This Week`. Secondary: https://wefunder.com/explore/all . Если direct reader получает только JS-shell, использовать domain-restricted search по этим URL/компаниям, затем открывать campaign pages.
- **Republic** — https://republic.com/companies . Проверять `Live opportunities` и метки `New`, затем открывать campaign page конкретного кандидата.
- **Springwise / Latest innovations** — https://springwise.com/home/ . Использовать блок `Latest innovations` и открывать конкретную innovation page.
- **Empire Flippers / новые operating businesses** — официальный публичный Marketplace API: https://api.empireflippers.com/api/v1/listings/list . Authentication не требуется. Для discovery запрашивать `listing_status=For Sale`, `sort=first_listed_at`, `order=DESC`, `limit=100`, начиная с `page=1`; при необходимости пагинировать. Документация: https://empireflippers.com/marketplace-api/ . HTML fallback: https://empireflippers.com/marketplace/ . Соблюдать лимит API не чаще 1 запроса/сек.
- **Starter Story / свежие кейсы** — primary: https://www.starterstory.com/episodes . Там видны свежие episodes и revenue figures; открывать конкретный кейс. Secondary: https://www.starterstory.com/ .

Использовать эти сайты как discovery, а не как автоматический whitelist. При необходимости искать дополнительные источники по всему интернету. Не прекращать обход из-за лимита места в отчёте: лимит применяется только на этапе финального отбора.

### Что отбирать

- понятный продукт/услуга и понятный покупатель;
- интересная, воспроизводимая или необычная бизнес-модель;
- реальный коммерческий потенциал или уже видимый спрос/traction;
- модели из разных ниш, а не только tech/AI;
- physical/DTC-проекты: знакомый рынок + ясный product wedge + доказанный спрос через preorder/crowdfunding — хороший ориентир;
- для crowdfunding не выбирать проект только по `% funded`: читать страницу, rewards/pricing, команду, аудиторию и фактическое число backers/raised;
- для Wefunder/Republic данные из pitch считать заявлениями компании, если они не подтверждены независимо;
- fundraising-источники используются только для изучения бизнес-моделей, не как инвестиционная рекомендация.

Обычно не брать настольные игры, книги, комиксы, кино и арт только потому, что они много собрали; novelty-gadgets без понятного бизнеса; generic AI wrappers; проекты без ясного customer/value proposition; проекты, где вся ценность — необычность, а не бизнес.

Саммари — **2–4 плотных предложения**: что продают, кому, как зарабатывают, какая traction/экономика известна. Без отдельной фразы «почему интересно».

Формат:

```md
## Бизнесы
### [Название бизнеса / проекта](PRIMARY_URL)
Что это, для кого, бизнес-модель и ключевые подтверждённые цифры: revenue/profit/backers/raised/pricing — что доступно и действительно полезно.
```

Если сильных бизнесов нет — раздел не выводить; добавить `Бизнесы` в финальную строку.

## 11. Product Hunt

Product Hunt — ежедневный радар того, что люди сейчас запускают и какие продуктовые тренды возникают, а не только поиск инструментов, которые лично полезны пользователю.

### Временная граница и точные URL

Product Hunt работает 24-часовыми днями по Pacific Time. На обычном ежедневном запуске определить **последний полностью завершившийся Product Hunt-день в `America/Los_Angeles`** и просмотреть все launches этого дня.

Основной официальный путь:

- calendar/archive root — https://www.producthunt.com/leaderboard
- точный daily archive — `https://www.producthunt.com/leaderboard/daily/YYYY/M/D/all`

`YYYY/M/D` подставлять без обязательных ведущих нулей. Обязательно использовать вкладку/суффикс **`All`**, а не только `Featured`: задача должна просмотреть весь доступный список дня, не top-5/top-10.

Если прямое открытие свежего daily URL даёт `cache miss`, это **не означает, что релизов нет**. Последовательно:

1. открыть https://www.producthunt.com/leaderboard и перейти по календарной ссылке нужной даты;
2. открыть точный `.../daily/YYYY/M/D/all`;
3. выполнить domain-restricted search по точному daily URL/date;
4. открыть найденные Product Hunt product pages и сайты/repo сильных кандидатов.

Если после этих попыток полный `All`-лист свежего дня всё равно недоступен, Product Hunt нельзя объявлять пустым: отметить неполное покрытие только в служебном результате запуска.

Официальный API существует по адресу https://api.producthunt.com/v2/api/graphql , документация — https://www.producthunt.com/v2/docs , но API требует access token. **Не рассчитывать на API как на обязательный путь, пока отдельный Product Hunt token явно не настроен.** Если токен будет настроен в будущем, API с `postedAfter`/`postedBefore` и pagination можно использовать как структурированный fallback для полного списка дня, а leaderboard — для финального score/rank.

Если автоматизация пропустила день, просмотреть все полностью завершившиеся Product Hunt-дни с прошлого отчёта, чтобы ничего не потерять.

### Критерий отбора

Отбирать продукты, которые показывают новый product pattern или тренд; необычно решают понятную проблему; демонстрируют интересную упаковку, distribution или business model; полезны для насмотренности; имеют настоящую продуктовую идею, даже если продукт не нужен пользователю прямо сейчас.

Перед включением открыть Product Hunt page и сам продукт; для technical/open source — repo/docs. Проверить, что это не старый relaunch без существенного изменения.

Не брать generic AI wrappers, AI slop, почти одинаковые клоны, thin UI над API и бессодержательные launches. **Upvotes — вторичный сигнал, не критерий качества.**

Саммари — максимально короткое и простое: что это и что конкретно делает/чем отличается. Обычно 1–2 коротких предложения.

Формат:

```md
## Product Hunt
### [Название](PRODUCT_HUNT_URL) · **N upvotes**
Что это и что делает/чем отличается — 1–2 коротких предложения.
```

Отдельную строку `Сайт`, `Сайт / GitHub` не добавлять. Если внешняя ссылка критична — встроить её естественно в саммари.

Если сильных продуктов нет после полного проверенного обхода — раздел не выводить; добавить `Product Hunt` в финальную строку.

## 12. Hacker News

HN — discovery-source, а не пересказ популярной ленты.

### Надёжный discovery

Для исчерпывающего обнаружения кандидатов использовать официальный HN API:

- top stories — https://hacker-news.firebaseio.com/v0/topstories.json
- new stories — https://hacker-news.firebaseio.com/v0/newstories.json
- best stories — https://hacker-news.firebaseio.com/v0/beststories.json
- конкретный item — `https://hacker-news.firebaseio.com/v0/item/ITEM_ID.json`
- при необходимости максимальный item id — https://hacker-news.firebaseio.com/v0/maxitem.json
- официальная документация — https://github.com/HackerNews/API

API возвращает до 500 top/new stories и отдельный best list. Использовать `time` item-а для фильтрации по реальному окну отчёта, `score` для текущих points и `url` для исходной статьи.

Дополнительные HTML-пути:

- front page — https://news.ycombinator.com/
- newest — https://news.ycombinator.com/newest
- most-upvoted за последние 24 часа — https://news.ycombinator.com/best?h=24
- комментарии конкретного item — `https://news.ycombinator.com/item?id=ITEM_ID`

API нужен для discovery и полноты, но перед включением обязательно прочитать исходную статью полностью и содержательные HN-комментарии на HTML item page.

Материал проходит, если даёт хотя бы одно: сильный новый результат по AI/coding agents; реально полезную новую технологию/dev workflow; важный business/founder/growth case с цифрами; крупный вывод по platforms/chips/infra/hardware; большой технический разбор, реально меняющий понимание важной технологии.

Не брать даже при большом количестве points: curiosity, niche bug hunt, историческую/Unicode/языковую историю, случайный gadget, indie story без сильных цифр/вывода, узкую техническую тему без заметной практической ценности.

Перед включением спросить: **«Я бы реально хотел получить push-уведомление именно об этом?»** Если нет — убрать.

Для каждого кандидата:

- прочитать исходную статью полностью;
- прочитать содержательные HN-комментарии;
- при необходимости собрать внешний контекст;
- в header показывать только points, без числа comments и без отдельной строки HN.

### HN-саммари

HN — главный содержательный раздел. Не ужимать до 1–2 предложений.

Саммари должно объяснять без открытия ссылки: что произошло / что построили / исследовали; исходный контекст; ключевой механизм или решение; важные цифры и результаты; ограничения или роль человека, если существенна; основной практический вывод. Обычно **4–7 плотных предложений**, без воды.

Формат:

```md
## Hacker News
### [Название статьи](ARTICLE_URL) · N points
Подробное, плотное, самодостаточное саммари.
> **[Комментарии](HN_URL)**
> 1–3 самых полезных аргумента/контраргумента.
```

Если содержательных комментариев нет:

```md
> **[Комментарии](HN_URL)**
> Ничего нет
```

В комментариях сразу давать аргументы, без мета-фраз.

`>` используется только для читаемого GitHub Markdown. Telegram CI не показывает это как blockquote: комментарии рендерятся обычной компактной строкой `Комментарии: ...`, где `Комментарии` — жирная кликабельная ссылка на HN.

Если сильных HN-материалов нет — раздел не выводить; добавить `Hacker News` в финальную строку.

## 14. Telegram / CI

Workflow: `.github/workflows/telegram.yml`.

`YYYY-MM-DD.md` одновременно архивная версия и источник текста Telegram-поста.

**Ключевое правило: один dated `.md` = один Telegram-пост.**

- при первой публикации нового `YYYY-MM-DD.md` вызвать `sendMessage` и сохранить полученный `message_id`;
- при любом последующем изменении этого же файла использовать только `editMessageText` для сохранённого `message_id`;
- никогда не отправлять второй Telegram-пост для того же `YYYY-MM-DD.md`;
- если файл уже существовал/публиковался, но `message_id` неизвестен, не отправлять дубль: остановить публикацию и потребовать однократно привязать существующий `message_id`;
- mapping `YYYY-MM-DD.md → message_id` хранить персистентно в `.telegram-state.json`;
- manual dispatch должен позволять передать existing `message_id`, привязать его к dated-файлу и сразу отредактировать существующий пост.

Текущая конфигурация:

- Telegram channel: `@kernnews`;
- GitHub Actions secret: `TELEGRAM_BOT_TOKEN`;
- бот должен быть администратором канала с правом публикации/редактирования сообщений;
- сам токен никогда не хранить в `INSTRUCTIONS.md`, workflow или dated-файлах.

Формат Telegram:

- публиковать dated `.md` текстом, а не файлом;
- не добавлять дату и отдельный заголовок;
- сохранять ссылки и bold;
- делать пустую строку только перед новым `##` разделом;
- внутри раздела не вставлять пустые строки между материалами;
- перед финальной строкой `Ничего нового: ...` всегда вставлять одну пустую строку;
- списки с `-` при рендере нормализовать в `—`;
- HN `>`-блоки не превращать в Telegram blockquote; рендерить обычной строкой: кликабельное жирное `Комментарии:` + текст;
- отключать link previews;
- публиковать одним сообщением, если помещается;
- если текст превышает безопасный лимит — падать, а не молча урезать.

## 15. Как настроить на другом ChatGPT-аккаунте

Сценарий: используется тот же GitHub-аккаунт и тот же уже настроенный репозиторий `p0dyakov/kernnews`. Репозиторий, GitHub Actions, Telegram bot, `TELEGRAM_BOT_TOKEN`, `.telegram-state.json` и архивные отчёты уже существуют и не создаются заново.

Если на новом ChatGPT-аккаунте пользователь присылает ссылку на этот `INSTRUCTIONS.md` и пишет «настрой», сделать только следующее.

### 15.1. Подключить существующий GitHub

Подключить GitHub integration/connector нового ChatGPT-аккаунта к существующему репозиторию:

- owner: `p0dyakov`;
- repository: `kernnews`;
- branch: `main`;
- нужен read/write access к repository contents.

Проверить, что ChatGPT может прочитать `INSTRUCTIONS.md`, прочитать последние `YYYY-MM-DD.md` и создать/обновить файл в `main`.

**Не создавать новый репозиторий, Telegram workflow, бота, secret или `.telegram-state.json`.** Если write-доступа нет — исправить доступ к существующему `p0dyakov/kernnews`.

### 15.2. Создать scheduled task

Создать **одну** задачу, без дублей.

Название: `AI + HN Digest`.

Расписание: каждый день **11:15 Europe/Moscow**, timing mode `exact_schedule`.

```ical
BEGIN:VEVENT
DTSTART;TZID=Europe/Moscow:20260818T111500
RRULE:FREQ=DAILY
END:VEVENT
```

При настройке `DTSTART` заменить на ближайшую будущую дату, сохранив `11:15 Europe/Moscow`.

Prompt:

```text
Это сложный многошаговый research workflow. На каждом запуске используй высокий уровень размышлений (High / extended reasoning), с приоритетом качества и полноты проверки, а не скорости.

В начале каждого запуска открой через GitHub актуальный файл `INSTRUCTIONS.md` из репозитория `p0dyakov/kernnews` и считай его единственным источником истины для ежедневного отчёта. Не используй закэшированные правила и не дублируй бизнес-логику в prompt. Строго выполни текущую версию `INSTRUCTIONS.md`, включая определение окна, ресёрч, retrieval fallback, проверку последних выпусков, формат, GitHub output и публикацию. Если `INSTRUCTIONS.md` недоступен, не импровизируй и сообщи об ошибке.
```

### 15.3. Проверка

После настройки проверить:

- scheduled task существует в одном экземпляре и стоит на `11:15 Europe/Moscow`;
- новый ChatGPT-аккаунт имеет read/write доступ к `p0dyakov/kernnews`;
- существующий `.github/workflows/telegram.yml` остаётся без изменений.

Тестовый dated-файл или Telegram-пост без явной просьбы пользователя не создавать.

## 16. Правило изменения системы

При любом следующем согласованном изменении сначала обновить `INSTRUCTIONS.md`, затем при необходимости привести текущий выпуск/CI в соответствие.

Scheduled task **не должен дублировать бизнес-логику**: он всегда просто перечитывает свежий `INSTRUCTIONS.md`. Менять scheduled task нужно только если меняется его расписание, репозиторий или bootstrap-prompt.
